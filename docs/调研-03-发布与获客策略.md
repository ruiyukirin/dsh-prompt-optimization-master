## 结论先行（TL;DR）

1. **渠道是真实的，而且只有一条主干**：`awesome-dsh-plugin` 精选列表（提 PR 加一个 YAML 文件）→ 自动同步到 `dshmarket` 插件市场、`awesome-dsh-plugin.com` 站点、`dsh-find-plugin` 的会话内搜索。**dshmarket 本身不是投稿渠道**，它的 README 明确写着拒收插件条目（来源：`dshmarket/README.zh.md:98`）。所以「上架」这件事只有一个动作：**给精选列表提一次 PR**。
2. **入局是红海，但不是完全没位**：严格按名字匹配的同类插件已有 **17 个**（来源：注册表 `registry.json`），放宽到描述含「提示词 + 增强/润色/优化」有 **28 个**。17 个里 **13 个集中在 2026-08 上架**，也就是这个位置在两个月内被填满了；但 **头部只有 1 个**（Fishsb/dsh-prompt-enhancer ★86），第 2 名就掉到 ★20 —— 典型的「一个头部 + 一堆长尾」，说明**还有位，但要靠明显不同的点切入**，靠「一键优化 + 可撤销」这种同质功能没有位置。
3. **两个必须马上处理的硬阻塞（本次调研最重要发现）**：
   - **npm 裸名 `dsh-prompt-enhance` 已经被别人占了**。该包由 `rongxingda` 持有，最新 `0.2.7`，已发 20 个版本，首版 `2026-08-29`（来源：`https://registry.npmjs.org/dsh-prompt-enhance`）。我们**不能**用这个包名发布，只能用 scope 名（实测 `@ruiyukirin/dsh-prompt-enhance` 返回 404，可用）。
   - **GitHub 仓库根本不存在**：`gh api repos/ruiyukirin/dsh-prompt-enhance` 返回 **404 Not Found**；本地目录 `D:\DeepSeek Harness\插件\dsh-prompt-enhance` 也**不是 git 仓库**（`git status` → `fatal: not a git repository`）。而 `package.json` 里的 `homepage` / `repository` / `bugs` 三个字段现在全都指向这个 404 地址。**这必须先补上，否则任何渠道都进不去**（精选列表收 `url` 必须与真实仓库完全一致）。
4. **最能打的是「推理预算与截断保护」这一条，不是「一键还原」**。「三态可撤销」已经是行业标配（17 个同类里至少 6 个明确写了可撤销/回填），而「一次短改写推理吃掉 2632 字符、512 token 预算下可见输出为 0、所以我们把上限提到 4096 并把触顶单独报成 `truncated`」是同类里罕见的**可复现量化事实**，而竞品恰恰在「静默失败」上翻车（seven282/oss-prompt-optimizer issue #3 就是「设置界面假成功」）。
5. **发布后要背的最大责任是「跟着宿主改」**：同类插件的真实 issue 几乎全是 DSH 版本升级打挂的 —— `slots.inject` 两段式注册被移除、`useInput`/`inputActions` 被移除、`settingsScope` 服务被移除（Y1X1n 的 issue #10 严重到 **DSH 直接打不开**）。DSH 启动是全有全无，一个插件加载失败整个进程退出（来源：`dshmarket/README.zh.md:48`）。**发布 = 承诺长期跟随宿主 rc 线**。

| 要求 | 说明 |
|---|---|
| 一个文件 | `data/plugins/<owner>__<repo>.yml`，**一个 PR 最多 3 条**（最近 100 个加条目的 PR 里 88 个只加了 1 条） |
| `dsh.bundle` manifest | `package.json` 必须声明 `dsh.bundle`。**只声明 `dsh.client` 会被 CI 拒绝**（最常见的退回原因） |
| `cordis.patch.yml` | 需在仓库根存在 |
| 仓库创建满 **1 天** | CI 自动检查，过滤「PR 前几分钟才建好」的仓库 |
| 真实可用代码 | 占位仓库 / 纯 README 仓库不收 |
| 打 `dsh-plugin` topic | **硬性要求** |
| 描述必须真实 | 「描述会被当作对插件的声明，并与代码核对」，**夸大是让一个本来不错的插件被打回的主要原因** |
| 现役维护 | 定期扫描标记「仓库消失 / 已归档 / 长期停更」，汇总到跟踪 issue 后经确认移除 |
| 分类贴合实际 | 分类选得不准由维护者直接改，不打回 |

**流程：** fork → 加一个 YAML → 提 PR → CI 校验（条目数 → `dsh.bundle` → 仓库年龄 → `awesome-lint` 与站点构建）→ 维护者读目标仓库源码、逐条核对描述 → 合并后站点自动重建、市场次日生效。官方口径：**「站点和本市场会自动收录，通常一天内生效」**。

**曝光机制：**

- `plugins.json` 被 `dshmarket` **每次打开实时请求**（`dshmarket/README.zh.md:108`：「不使用过期缓存兜底」）；
- 每个条目生成一个 `/p/<owner>/<repo>/` 详情页；
- 卡片排序吃 **star 数 + 下载量**（下载量字段来自 npm，见渠道 ③）；
- 精选列表是 `dshmarket` 的**白名单**：`dshmarket/README.zh.md:62`：「**只允许安装 awesome-dsh-plugin 精选列表内的来源，其它一律拒绝**」——没进列表 = 用户在市场里根本装不到。

### 渠道 ④ GitHub Releases / `dsh-plugin` topic（**社区流量入口 + 收录硬性要求**）

### 建议的定位一句话（供 README / 列表描述用）

> **不会给你一个被截断的提示词。** 一次独立模型调用改写草稿（不进会话记录），推理开销计入预算，触发上限时明确报错而不是悄悄塞半句——因为截断的提示词比不优化更糟。

（描述措辞要遵守收录规则：「描述只说功能，不带营销词」，这句话是功能声明 + 可核对的行为契约，符合规则。）

### 差异化不足，应该补什么（**本次不改代码，仅建议**）

按「性价比 × 竞品差距」排序：

1. **必须补：模式档位。** 现在是单档。竞品明确有多档：Fishsb「5 模式」、zzy6-a「五种改写风格」、oss-prompt-optimizer「三种输出形态」、`dsh--prompt-enhance`（sunzhentao）「基础/标准/专家三档」。**零档位 = 用户找不到「我要更短一点」的出口**，这是最大的功能性落差。
2. **值得补：差异预览（前后对照）。** `DIAG5/dsh-better-input`（★30，月下载 2299）已做「带差异预览的提示词优化」，rongxingda 也有「前后对比」。本插件现在是「结果直接替换输入框」，**用户看不到改了什么**，第一次用会有不信任感。
3. **值得补：保真校验。** `hoyyang/dsh-improve-prompt` 已做「机械校验硬事实（路径、标识符、数字）」。本插件 README 已声明「不许提用户没提的技术栈」——**把这条声明落成机械校验并写进测试**，就从「提示词自律」升级成「代码保证」。
4. **顺手就能做（零成本高回报）：把离线测试当卖点。** README:96-107 已有 38 项宿主半 + 24 项客户端半检查、`npm test` **不需要 DSH** 就能跑。对 17 个同类的双语描述做 `test/测试` 扫描，只有 **1 家**真的提了测试——`ZiYuan258/dsh-prompt-enhance` 的 `description.en` 结尾写着 **「204 tests.」**（其余命中是 "latest"/"connectivity test" 的误匹配）。也就是说这块位置**几乎空着，但已经有人先站住了**：本插件 62 项检查对 204 项，**下次宣传时应准确报数，不要用「同类唯一」这种会被一句话证伪的措辞**。对「怕插件把 DSH 搞崩」的用户，这是强信号（第五章会看到，把 DSH 搞崩是同类最常见的灾难）。
5. **不建议做**：语音输入（Fishsb 已做，且需要云端 ASR/本地模型，维护成本极高）、记忆链（rongxingda/Y1X1n 已做，与「不占对话上下文」的定位冲突）。**本插件最干净的差异化恰恰是「轻」**——不要为了堆功能破坏这个定位。

- 同时建 `v1.0.0` Release，附一个预构建 `.tgz`。**如果资产名里带版本号，就必须钉 release tag 而不是用 `latest/download/`**（官方原话：`latest/download/` 只在请求时解析 `latest`、文件名照字面取，带版本号会「提交当天有效、下一次发版就 404」）。
- 在 yml 条目里加一条 `tarball:` 指向它 —— 好处：预构建安装**免 `allowBuilds` 构建授权**，安装从「pnpm 构建」变成「解压」。

**B3. 在插件自己的 GitHub Discussions 发发布说明。**
- 为什么在这里：`dshmarket/README.zh.md:35` 写明评论底层是 giscus + GitHub Discussions，**「一个插件只有一处对话，而不是三处」**——你发一条，市场卡片、`dshmarket.com`、`awesome-dsh-plugin.com` 三个入口都能看到同一条。
- 内容：v1.0.0 做了什么 + 30 秒上手 GIF（复用 A3 第 2 张）+ 已知限制（写「限制」不写「未来计划」，避免形成承诺）。

**B4. 明确不要做的事：不去 `dsh-market/dsh-market` 提插件条目。**
- 该仓库 README.zh:98 原文：「**请不要往本仓库提插件条目。**」提了也是白费。

### 阶段 C：发布后

**C1. 建立「宿主 rc 跟版」例行任务（最高优先，每周一次）。**
- 动作：`npm view @deepseek-ai/dsh-* versions --json` 看官方包是否进入新的 rc/alpha 线；本机真机冒烟一次三段状态流转；发现破坏性变更 **24 小时内发 patch**。
- 依据：同类 17 个里的 issue 几乎全是版更打挂（详见第五章），rongxingda 的 6 个 open issue **全部**是这个原因，且它已 9 天未推送。

**C2. issue 响应策略：48 小时内首次响应 + 三类固定模板。**
- 同类 issue 的实际主题分布（实测，见第五章）可归为三类，直接为每类写一条模板：
  1. **装不上 / 激活失败**（`pending (waiting for service: …)`、`插件无法激活`）→ 模板要求贴 4 样：DSH 版本、插件版本、出错阶段（启动 or 刷新页面）、`~/.dsh/profiles/<名字>/cordis.patch.yml` 相关行。
  2. **按钮不出现**（`Enhance button never renders`、`composer button not rendered`）→ 先问「宿主半起来了没有」（本插件 README:88-92 已写明：客户端改动刷新页面、宿主改动重启 DSH，这条正好可以拿来当第一回答）。
  3. **静默失效 / 假成功**（`设置界面假成功`、`设置分区静默失效`）→ 本插件已有 `truncated` 独立错误码，**把所有错误码在 README 里列成表**，用户一对照就知道是不是静默失败。
- 依据：`seven282/oss-prompt-optimizer` 的 5 个 open issue 里，#3 是「设置界面假成功」、#5 是「设置按钮语言回退」、#2 是宿主接口参数变更——**这三类占了全部**。

**C3. 打「永不静默失败」这张牌，并用测试锁死。**
- 把第五章的同类 issue 当作素材写进 README 的「为什么这个插件不会悄悄失败」小节（引用公开 issue 编号，不评价作者）。
- 本插件已有 38 + 24 项离线检查，**每次发版在 Release note 里贴 `npm test` 的通过条数**。这是唯一能对抗「插件把 DSH 搞崩」恐惧的公开证据。

**C4. 每月复查一次市场数据（10 分钟）。**
- `node D:\DeepSeek Harness\插件\.wb-research\market-prompt-plugins.mjs` 重跑，看自己是否进榜、star/下载排名是否变化。
- 单独对一次 npm 下载量：`https://api.npmjs.org/downloads/point/last-month/@ruiyukirin%2Fdsh-prompt-enhance`（口径已验证与 registry 的 `downloads` 一致，见渠道 ③）。
- 若 3 个月月下载 < 100：不要加功能，先改**双语描述关键词**（市场按中英描述 + 分类做搜索命中；`dsh-find-plugin` 在 GitHub 搜索失败时会回退到精选列表的关键词匹配），把「提示词优化 / prompt enhancer / 润色 / 改写」这类用户实际会打的词补进 `description.en/zh` 与 README（**但必须与功能一致，描述真实性是硬规则**）。

**C5. 版本迭代节奏建议：小步快跑，每次 ≤ 3 天工作量。**

### 5.2 发布后必须承担的长期维护责任（清单）

| # | 责任 | 具体内容 | 依据 |
|---|---|---|---|
| R1 | **跟随宿主破坏性变更** | `slots.inject` 两段式注册、`useInput`/`inputActions` 插槽 props、`settingsScope` 服务、`commands/execute` 参数个数 —— 这些都已被移除或改签名。本插件用的是 `conversation.input.right` 插槽 + `useInput`/`inputActions`（README:34-39），**正好落在已被改过两次的那个契约上**，风险等级最高 | rongxingda #4 #3 #2、Y1X1n #10、seven282 #2 |

### 5.3 与「发布」捆绑的额外风险提示

- **同名混淆风险（高于一切其他风险）**：`dsh-prompt-enhance` 这个名字在市场里有 **3 个条目**（rongxingda / zzy6-a / ZiYuan258），npm 上是 rongxingda 的包。若我们不改名就发安装命令，**用户会装到别人的插件上**。这条必须在 A2 一步解决，并与命名调研任务（naming-researcher）的最终结论对齐。
- **`dsh-prompt-enhance` 的 owner `rongxingda` 与我们无任何关系**，其包 `maintainers` 邮箱、`repository` 均指向该作者；**不要**在任何文档里暗示与该包同源。
- **未验证项**：本报告未评估本插件在 DSH 未来版本上的实际兼容性（未做跨版本真机验证）；未统计精选列表 PR 的实际审核时长分布；未核实 `dshmarket.com` 与 `awesome-dsh-plugin.com` 的独立访问量（无公开数据）。
