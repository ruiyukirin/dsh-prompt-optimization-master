## 结论先行

**你的问题不是"描述写得不好"，也不是"没截图"，而是"没人知道你存在"。**

三个数字说清处境：

| 指标 | 你的值 | 参照 |
|---|---|---|
| npm 月下载 | **558** | 同类头部 `dsh-prompt` 10,598、`dsh-prompt-enhance` 7,210 |
| GitHub star（星标） | **1** | 同类头部 26、55 |
| 社区目录全库排名（按下载） | **第 2851 / 3426** | 中位数是 1086，你在中位数以下 |

而全库统计给出一个很硬的事实：

| 分组 | 条目数 | 月下载中位数 |
|---|---|---|
| star ≥ 10 | 710 | **2,539** |
| star < 10 | 2,714 | 963 |

**star（星标）过了 10 这条线，月下载中位数是过去的 2.6 倍。** 下载量前 50 名里，**49 个** star 都 ≥ 10。

所以本方案的主攻方向非常明确：**把 star 从 1 拉到 10 以上，让"最热"排序里出现你**。这一步过不去，后面所有优化都是给已经知道你的人数百分点。

## 一、先纠正两个直觉错误（都有数据）

### 错误一：以为"加截图"能大幅提升下载

全库对比：

| 分组 | 条目数 | 月下载中位数 |
|---|---|---|
| 有截图 | 911 | 1,223 |
| 无截图 | 2,513 | 1,052 |

**只差 16%。** 截图不是决定因素。但在你这个细分赛道里，截图是**稀有品**：下载前 10 的提示词类插件里，只有第 1 名（`FeatherHunter/dsh-prompt`，10,538 次下载，8 张截图）做了。

→ 结论：截图要做，但它是**锦上添花**（第 3 批做），不是主攻。

### 错误二：以为"发版频率越高越好"

竞品 `dsh-prompt` 73 个版本、`dsh-composer-ux` 47 个版本，那是摸索期疯狂试错。你 4 个版本（0.3.0/0.3.1/0.3.2/0.3.3）反而更健康。

但有个社区调研值得注意：知乎那条 **182 赞**的推荐长文里，作者明确说判断"值不值得装"只看两件事之一——

> 「最近有没有持续发版本——还在发，说明作者还在管」

→ 结论：**发版不是越多越好，而是"看起来还在管"**。你现在 16 天发 3 版，这个信号已经很好了，问题是没有地方把它展示出来（见下面 A2）。

## 二、漏斗拆解：四个环节，各有各的短板

```
①被看见  →  ②点进详情页  →  ③决定装  →  ④装完不卸载
   ↑            ↑              ↑            ↑
 最短板        还行         缺证据        靠发版信号
```

| 环节 | 现在的问题 | 对应动作 |
|---|---|---|
| ① 被看见 | 目录里排第 2851、star=1，市场"最热"排序里根本翻不到 | **B 组（内容分发）** |
| ② 详情页 | 有中英双语描述、有 `dsh-plugin` 标签，这块基本合格 | A3 小修 |
| ③ 决定装 | README 里没有"为什么选这个而不是竞品"的对比表 | A3 |
| ④ 装完不卸载 | 0.3.3 刚加了 CI 和 204 项测试，但**没人知道** | A2、A3 |

## 三、动作清单

### A 组：仓库侧（纯自己动手，1–2 小时，不用求人）

#### A1. 补 GitHub Release（**现在缺**）

现状：仓库只有 git tag（`v0.3.0`–`v0.3.3`），**没有一条 Release（发行版）**。

为什么重要：
- Release 页面是 GitHub 上唯一"按版本浏览"的入口，也是别人搜 `dsh-plugin` 时能撞到的页面；
- 很多目录/榜单按 `pushed_at`（最后推送时间）和 release 活跃度排序；
- 你现在每次发版的 CHANGELOG 已经写得很完整，**白写了没人看**。

怎么做：以 `v0.3.3` 为例，把 `CHANGELOG.md` 里 `## [0.3.3]` 那一段直接粘贴成 Release 说明，标题写「0.3.3 — 模型选择改下拉框、错误提示不再藏起来」。以后每次发版都建一条。

成本：5 分钟/次。

#### A2. 给社区目录条目补截图和图标（要提 PR，但改动极小）

现状（权威证据，目录仓库里的条目文件）：

```yaml
url: https://github.com/ruiyukirin/dsh-prompt-optimization-master
name: ruiyukirin/dsh-prompt-optimization-master
category: ui
description:
  en: Adds a button to the composer...
  zh: 在输入框加一个按钮...
```

**没有 `screenshots`，也没有 `icon`。**

全库现状：6,704 条里只有 **1,494 条（22%）** 有截图，只有 **13 条** 有图标。这是个低竞争的身位。

截图 URL 的形式（已核实头部插件的写法，都是仓库里的原图直链）：
- `https://raw.githubusercontent.com/<owner>/<repo>/main/assets/xxx.png`（PNG / JPG / GIF 都行）
- 也可以指向 GitHub Releases 附件（`.../releases/download/media-v1/xxx.gif`）

怎么做：在仓库建 `assets/` 目录，放 2–3 张真实截图（界面里那个按钮 + 增强前后的草稿 + 设置页），然后去 `awesome-dsh-plugin` 提 PR 改自己那条 YAML 加：

```yaml
screenshots:
  - https://raw.githubusercontent.com/ruiyukirin/dsh-prompt-optimization-master/main/assets/demo-zh.png
  - https://raw.githubusercontent.com/ruiyukirin/dsh-prompt-optimization-master/main/assets/demo-settings.png
icon: https://raw.githubusercontent.com/ruiyukirin/dsh-prompt-optimization-master/main/assets/icon-180.png
```

注意：**必须是真截图**（目录维护者会核对，用 AI 生成的假图有被打回风险）。

#### A3. README 首屏加"3 秒看懂"和"为什么不装别人"

现状：README 15,837 字节，内容很全（安装/配置/原理/实测记录都在），但**首屏是长段落**。

改两处就够：
1. **首屏顶部**放一张截图 + 三行大字：这是什么 / 解决什么痛点 / 一条安装命令；
2. 加一张**竞品对比表**，把你真正的差异点摆出来——这些是你已经有、但没人知道的东西：

| 能力 | 本插件 | 多数同类 |
|---|---|---|
| 语言锁（英文进英文出、中文进中文出） | 有 | 部分没有 |
| 一键还原原文 | 有 | 少数有 |
| 不建会话、不写会话记录、不读对话历史 | 有（默认） | 需逐个确认 |
| 会不会思考的模型都自适应输出预算 | 有（0.3.1 修复） | 多数硬编码 4096 |
| 自动化测试 | 204 项 + CI | 多数 0 |
| 兼容声明 | 显式 `engines.dsh` | 多数未声明 |

最后一行"204 项测试 + CI"是**刚做完 0.3.3 才有的新资产**，现在 README 里没突出。这是"专业感"最直接的证据。

### B 组：内容分发（**这才是主攻**，但需要你本人出面）

#### B1. 去知乎那条已有流量的问题下写一篇"开发者实测"

已核实的事实：
- 问题：**「DeepSeek Harness有哪些值得你推荐的插件?」**（知乎问题 id `2073459069575229735`）
- 该问题下现有高赞答案：**298 赞**（2026-10-20）、**182 赞**（2026-09-24）、27 赞（2026-10-03）
- 说明：**这个问题是活的，有真实流量**

为什么这条最有效：它是"正在找插件的人"聚集的地方，比任何 SEO 文章都精准。

**怎么写（关键，决定成败）：**
- ❌ 不要写成安利帖（"强烈推荐这个神器！"）——这类内容会被折叠，也不符合你自己反感标题党的口味；
- ✅ 写成**开发者的实测复盘**：「我做了个提示词增强插件，踩了 3 个坑，第 1 个是 DSH 的推理预算」——用 0.3.1 那个真实的 bug（写死 4096 输出预算，遇到会思考的模型直接截断）当故事主线，最后顺带给出安装命令；
- ✅ 附真实截图（不是渲染图）；
- ✅ 明确说清"不建会话、不写会话记录"这个隐私设计。

成本：一篇 2–3 小时。

#### B2. 版本即内容（可持续，成本最低）

已核实的对标案例：知乎作者 **李二牛li2niu** 给 `dsh-plugin-garmin-connect` **每发一版写一篇**，其自述"月下载量已经接近 3k"。

你现在的条件是**完全具备**的：`CHANGELOG.md` 已经按版本写好、每次发版都有真实内容（0.3.2 改兼容声明、0.3.3 改下拉框+CI）。

怎么做：每次发版 → 同一天发一条短内容（知乎想法 / 回答更新 / GitHub Release 正文三处复用同一段文字）。**不要为了发文而发版**，反过来：**发版了才发文**。

成本：30 分钟/次。

#### B3. 让 DSH 用户在官方渠道能搜到你

已核实：你的 GitHub 仓库已有 5 个 topics（`deepseek-harness` / `dsh` / `dsh-plugin` / `prompt-engineering` / `workbuddy`），**这部分已经合格，不用改**。

补充动作：在 DSH 官方仓库的 Discussions（讨论区）里找"插件分享"类帖跟进（若有）。这条需要现场确认，不预设结论。

| 指标 | 现在 | 30 天目标（保守） | 30 天目标（争取） |

| GitHub star | 1 | 10（过关键线） | 30 |

**唯一不能造假、也最能说明问题的指标是"周下载"。** star 可以靠一篇爆帖冲上去，下载才是真装。

  Where-Object { $_.name -eq 'dsh-prompt-optimization-master' }

## 六、明确不建议做的事（避坑）

| 别做 | 为什么 |
|---|---|
| 买 star / 刷下载 | 目录会定期扫描标记，且 GitHub 会清理；一旦被抓，插件被移出精选列表 = 前功尽弃 |
| 写标题党长文发到内容农场 | 你自己的偏好就反感这类内容；而且这类页面的读者不会装插件 |
| 和 `dsh-prompt-enhance` 公开对比互撕 | 引战只会给对方导流；对比表放自己 README 里就够 |
| 为了发文而频繁发版 | 会让版本号失去意义，也让维护成本失控 |
| 一次性铺满所有渠道 | 一个人维护不过来，且各渠道文案要求不同；先做透 1 个（知乎）再加第 2 个 |

## 七、代价与长期责任（说实话）

- **时间**：本周约 4 小时（A 组 + PR），B1 那篇约 3 小时，之后每次发版约 30 分钟写内容。
- **长期**：进了精选列表就要**持续维护**——目录会定期扫描"仓库消失 / 已归档 / 长期停更"的条目并移除。你已经 16 天发 3 版，这个节奏保持住就不会被清。
- **风险**：曝光上来后会有 issue（问题单）和功能请求。目前仓库 0 个 issue，一旦有流量就会变。建议在 README 写明"接受什么、不接受什么"，先立规矩。
